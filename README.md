# AegisAgent: Fraud Detection & Automated STR Drafting

AegisAgent scores card transactions with a stacked ML ensemble and drafts
FINTRAC-style **Suspicious Transaction Report (STR)** narratives for the ones that
breach the decision threshold. It is a portfolio/research project built on a public
synthetic dataset, not a production compliance system — see
[Scope & limitations](#scope--limitations) before reading anything else.

The models originate from an MSc capstone (*Feature-Enhanced Machine Learning Models
for Credit Card Fraud Detection*, Memorial University of Newfoundland); this repo is
the data-engineering, serving and reporting layer built around them.

---

## Current model performance

Measured on the held-out test split (`fraudTest.csv`, 555,719 transactions,
2,145 frauds — 0.39% prevalence). Numbers come from
`models_artifacts/<version>/training_metrics.json` and are regenerated by
`scripts/train_models.py`.

| Metric | Value |
|---|---|
| **PR AUC (meta)** | **0.8010** |
| ROC AUC (meta) | 0.9941 |
| Precision | 84.8% |
| Recall | 69.8% |
| F1 | 0.766 |
| Frauds caught | 1,497 / 2,145 |
| Alert volume | 1,765 over 193 days (**9.1/day**) |
| Decision threshold | 0.5832 |

**PR AUC is the headline number.** At 0.39% prevalence a ROC AUC of 0.99 is not
impressive on its own — a model can rank well and still drown an investigations team
in false positives. Alert volume per day is reported for the same reason.

Base models (test ROC AUC / PR AUC): Model 2 geographic RF 0.9816 / 0.7679 ·
Model 3 category XGBoost 0.9874 / 0.7157 · Model 4 velocity RF 0.9909 / 0.7974.

## How it works

```
fraudTrain.csv ─┐
                ├─► dbt + DuckDB ──► fct_fraud_features ──► stacked ensemble ──► threshold ──► STR agent ──► compliance log
fraudTest.csv  ─┘   (staging →          (27 columns,        (RF + XGBoost         (0.5832)      (Bedrock)      (local + S3)
                     intermediate →      1.85M rows)         + RF → logistic
                     marts)                                  meta-learner)
```

**Feature layer (dbt → DuckDB).** Staging views read the raw CSVs; intermediate
models derive Haversine distance from home, cyclical hour encodings, category /
state / merchant target encodings, per-card spend statistics and trailing 24h/7d
transaction velocity. The mart `fct_fraud_features` is the single contract the
models consume.

**Model layer.** Three base learners (geographic RF, category XGBoost, velocity RF)
feed a logistic-regression meta-learner. Split discipline is chronological
throughout — 70% base / 15% blend / 15% calibration on the training year, with
`fraudTest.csv` untouched until final evaluation. The blend split fits the
meta-learner; the calibration split, which neither the base models nor the
meta-learner have seen, selects the decision threshold.

**Reporting layer.** Alerts are sent to AWS Bedrock (Claude Haiku 4.5) with a 5W+H
STR prompt. A retry loop rejects hedging language; narratives that still fail after
retries are written to `compliance_logs/quarantine/` for manual review rather than
discarded. Card numbers and names are masked before they leave the process.

## Setup

**Prerequisites:** Python 3.11+, Docker (optional), AWS credentials with Bedrock
access (only for STR generation).

```bash
git clone https://github.com/haseebkn/aegisagent.git
cd aegisagent
python -m venv venv && source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

Download `fraudTrain.csv` and `fraudTest.csv` from the
[Kaggle Credit Card Transactions Fraud Detection dataset](https://www.kaggle.com/datasets/kartik2112/fraud-detection)
into the repo root, then:

```bash
dbt run --profiles-dir .
dbt test --profiles-dir .
python scripts/train_models.py
streamlit run app.py
```

Every path is env-overridable (`DBT_DB_PATH`, `MODELS_ARTIFACTS_DIR`,
`COMPLIANCE_LOGS_DIR`, `AEGIS_RAW_DATA_DIR`) and defaults to a location relative to
the repo root — see `scripts/config.py`.

### Container

```bash
docker build -t aegis-app:latest .
docker run --rm -v "$PWD/aegis_db.duckdb:/app/aegis_db.duckdb" aegis-app:latest
```

The image carries the dbt project, scripts and model artifacts. The DuckDB file and
raw CSVs are data and are mounted at runtime.

## Data quality controls

`dbt test` runs eight checks. Three are worth calling out because they encode bugs
this project actually shipped:

| Test | Guards against |
|---|---|
| `assert_velocity_no_train_serve_skew` | Velocity features being computed differently at training and scoring time. An earlier version filtered the window on `dataset_split`, which zeroed `txns_24h`/`txns_7d` for 99.5% of test rows while training saw real counts. Null checks passed throughout — zero is not null. |
| `assert_no_degenerate_feature_scale` | Divide-by-epsilon on cards with no history, which produced `amt_z_card` values in the billions that were rendered into STR prompts as fact. |
| `assert_row_count_matches` | Silent row loss in the join/union chain. |

`scripts/verify_pipeline.py` runs the same skew check plus an end-to-end pass:
dbt tests → schema/row checks → live inference bounds → STR generation on the
highest-scoring real transaction in the test split.

## Scope & limitations

Read this before drawing conclusions from the metrics above.

- **The data is synthetic.** It comes from the Sparkov generator, not real card
  traffic. Simulated fraud has deterministic artefacts that models learn and that do
  not exist in production. The absolute numbers do not transfer.
- **Card fraud is not money laundering.** STRs are AML instruments. Fraud is a
  predicate offence, so proceeds-of-fraud STRs are legitimate, but this project uses
  an STR format on a card-fraud dataset for demonstration purposes. Narratives are
  drafting aids, not filings.
- **LLM narratives are not verified for factual grounding.** The retry loop screens
  hedging language only. It does not check that claims in the narrative follow from
  the input payload, and generated text has been observed to assert facts it was
  never given. Every narrative needs human review. Closing this gap is the top item
  on the roadmap.
- **Target encodings are fit in-sample.** Category/state/merchant risk are computed
  over the full training split and applied back to training rows. With 693 merchants
  at 727+ rows each the practical leakage is small, but out-of-fold encoding is the
  correct treatment.
- **No drift monitoring, no champion/challenger, no analyst feedback loop.** These
  are prerequisites for anything operational.
- **Deployment is not continuous.** `deploy.sh` is a manual, Windows-oriented script
  that builds the image, pushes to ECR and applies Terraform. There is no CI
  pipeline. The ECS service is defined with `desired_count = 0`.

## Infrastructure (Terraform)

Defined in `terraform/`, applied manually:

- **S3 compliance bucket** with Object Lock in COMPLIANCE mode (5-year retention),
  versioning, SSE, full public-access block, and lifecycle transition to Glacier at
  90 days.
- **IAM** task role scoped to `bedrock:InvokeModel` and the compliance bucket; no
  static keys in the task definition. *Known gap: the Bedrock policy grants the
  foundation-model ARN but the code calls a cross-region inference profile, which
  also requires the profile ARN.*
- **VPC** with a public subnet, IGW and an egress-only security group.
- **ECR** with scan-on-push and untagged-image expiry.
- **ECS Fargate** cluster, task definition and service (`desired_count = 0`).
- Remote state in S3 with DynamoDB locking.

## Roadmap

1. Replace the hedging-word guardrail with factual grounding checks — assert every
   figure in a narrative traces to the input payload.
2. Out-of-fold target encoding; calibration curve for the meta-learner.
3. Cost-sensitive threshold selection driven by an explicit alert budget.
4. Entity/graph features (shared-merchant components, connections to known-fraud
   entities) — the signal supervised per-transaction models cannot see.
5. PSI/KS drift monitoring on the serving feature distribution.
6. CI running `dbt test` + `terraform validate` on every push.
