# Portfolio readiness audit — September 2026

Scope: application, HTTP service, feature pipeline, model training/evaluation and
governance, case/evidence workflow, privacy controls, tests, container, infrastructure
reference, thesis provenance and portfolio claims. This is an engineering audit,
not independent model validation, a penetration test or a compliance certification.

## Findings and fixes

| Area | Failure found | Resolution and regression evidence |
|---|---|---|
| Model governance | A valid event chain did not prove that the registry's current champion/status matched it; consistent fabricated comparison metrics could pass derived gates. | Replay committed registry state, verify artifact hashes before loading, and independently re-score the actual development holdout before registering comparison evidence. Governance tests exercise modified state, artifacts and reports. |
| Serving | Missing thresholds fell back to a different alert policy; some invalid rows were rounded or escaped validation; a cached dashboard model could outlive a promotion. | Reject invalid/missing policy and nonfinite/out-of-domain features across all rows. Resolve and verify the active immutable version on each dashboard rerun. Inference and registry regression tests cover rejection paths. |
| Validation | Chronological internal holdouts still carried encodings updated by labels within those windows. | Freeze blend, calibration and rolling-validation category maps at their fitting boundary. Ordinary training does not read locked-tail labels. Prior label availability remains a disclosed simulation assumption. |
| Evaluation | Capacity search could violate its hard limit; calendar exposure and constant-score calibration handling were inconsistent. | Exact threshold frontier, enforced alert budget, inclusive calendar-day exposure, and corrected constant-probability ECE. Behavioral evaluation tests cover edge cases. |
| Drift | Missing/empty/nonfinite inputs could produce an empty or misleading pass; sparse distributions needed safer PSI bins. | Require all monitored features and usable windows, fail on bad inputs, use robust bin edges, and default to development-only comparisons. |
| Feature engineering | Graph self-exclusion could subtract a fraud relationship not present in the historical graph. | Subtract only an actual prior fraud edge; graph features remain excluded from the predictive models. Add finite-feature and train-before-test dbt assertions. |
| Case integrity | Reopening a modern store could rehash corrupted history when a digest was blank; projection edits were insufficiently checked. | Limit backfill to real legacy schema migrations; verify status, assignment, timestamps, committed model fields and evidence metadata against history. |
| Evidence authorization | Rejected narrative attachments could write files or attempt cloud archival before authorization; changed model output could be attached to an older case. | Preflight principal, tenant, review state and version before preservation, then recheck under the write lock. Require narrative model version and score to match the case alert. |
| Security boundaries | Boolean-like payloads could be coerced; explicitly injected development identities could reach production checks; dynamic narrative HTML was not uniformly escaped. | Strict request models and boolean decisions, production rejection of local identities, escaped rendering and provider-output redaction. |
| Resource lifecycle | SQLite transaction context managers did not close connections, leaving Windows files locked. | Explicit close on success and failure; regression test retains connection handles and proves they are closed. |
| Dependencies | Vulnerable Streamlit, Starlette and sqlparse versions were installable. | Update Streamlit and compatible FastAPI/dbt parents, pin patched transitive versions, add full dependency auditing to CI and pip Dependabot updates. |
| Demonstration/deployment | Fresh reviewers needed large data and optional cloud services; deployment defaults implied more readiness than delivered. | Isolated synthetic demo, real dashboard interaction smoke test, loopback-only Compose binding without ambient AWS credentials, cloud-free deployment preflight and explicit dormant reference provisioning. |
| Portfolio claims | Historical numbers and current code could be mistaken for the same protocol; below-threshold UI labels implied safety. | Explicit historical-result caveats, neutral alert labels, thesis/project separation, security disclosure policy and a reviewer walkthrough. |

## Reproducible verification

Use Python 3.11 and install `requirements-dev.txt`, then run:

```bash
python -m pytest
python -m ruff check .
python -m scripts.demo
```

The demo generates 14,500 synthetic rows in a new `.demo/run-*` directory, builds
seven dbt models, trains actual fixture artifacts, runs 17 data tests, checks
inference and case/evidence integrity, evaluates all 19 drift features, and exercises
dashboard selection, case creation, assignment and integrity verification. It makes
no Bedrock calls and records no RGS disposition. The fixture is intentionally easy;
its excellent classification metrics are **not evidence of real-world effectiveness**.

Local verification during this audit included 232 passing unit tests under Python
3.11, lint, the synthetic data/model/case workflow, dashboard interaction testing,
Terraform formatting/validation with no backend, and a full application-dependency
audit (including test dependencies) with no known vulnerabilities reported after
updates. The container also completed the entire demo with networking disabled and
no host mounts; its packaged legacy models loaded under the non-root default
production-mode identity. Synthetic training uses two workers to avoid CPU
oversubscription on large-core hosts. GitHub CI is the
release-specific evidence for the pushed commit; consult its current result rather
than assuming a historical local pass proves a later change.

## What was deliberately not done

- No production deployment, AWS provisioning, paid narrative generation, real
  customer-data processing or regulatory submission.
- No Clerk integration: production mode remains fail-closed until verified identity
  and organizational-role mapping are implemented and tested.
- No overwrite of original research artifacts or historical evaluation reports.
  Revised full-dataset training and development-only evaluation still need a governed
  run before quoting new performance figures. The locked tail was not reopened.
- No assertion that SHA-256 chains resist an administrator who rewrites both data
  and hashes. Independent audit retention, signed provenance and managed storage are
  production requirements.
- No claim that local single-process deployment establishes multi-instance safety,
  retention compliance, backup recovery, service-level performance or bank approval.

## Presentation guidance

Present this as a **fraud-investigation engineering portfolio**, demonstrating
temporal validation, explicit model limitations, governed promotion, human review and
traceable evidence. The strongest interview story is identifying and correcting
failure modes, not describing synthetic scores as production accuracy. See the
[reviewer walkthrough](portfolio.md) and [model card](../MODEL_CARD.md).
